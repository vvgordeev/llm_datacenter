llm 0.37.2: две тихие дыры, через которые свой ключ OpenAI уходил на чужой эндпоинт llm 0.37.2: two quiet holes that sent your real OpenAI key to someone else's endpoint

Релиз на GitHub ↗GitHub release ↗

11 ноября Саймон Уиллисон выпустил патч-версию 0.37.2 своей консольной утилиты llm — инструмента, которым он сам и множество разработчиков обращаются к разным провайдерам моделей из одного CLI. Релиз закрывает две уязвимости безопасности (GHSA-v9h7-jj4g-f862 и GHSA-r639-rr7r-x72w), обе — про один и тот же класс ошибки: при настройке «псевдо-OpenAI»-эндпоинта (стороннего сервера с OpenAI-совместимым API, указанного через api_base в extra-openai-models.yaml) llm в определённых условиях всё равно подставлял в запрос настоящий ключ из OPENAI_API_KEY или сохранённый ключ провайдера openai — то есть секрет, выданный Anthropic… простите, OpenAI, уходил на домен, который пользователь сам вписал как «ещё один OpenAI-совместимый сервер». On November 11, Simon Willison shipped 0.37.2, a patch release of llm, the command-line tool he and many other developers use to talk to multiple model providers from one CLI. The release closes two security advisories (GHSA-v9h7-jj4g-f862 and GHSA-r639-rr7r-x72w), both the same class of bug: when you point llm at a third-party, OpenAI-compatible endpoint (via api_base in extra-openai-models.yaml), under certain conditions it still attached your real OPENAI_API_KEY or your stored openai provider key to the request — meaning a secret issued by OpenAI ended up on whatever domain you'd configured as "just another OpenAI-compatible server."

Механика двух дырHow the two holes worked

Первая (GHSA-v9h7-jj4g-f862) касалась моделей, у которых в конфиге указаны и api_base, и api_key_name — то есть автор явно просил llm брать для этого эндпоинта отдельный, именованный ключ. Если такой ключ не был сохранён (пользователь просто не успел его добавить), инструмент раньше не отказывал в запросе, а тихо подставлял вместо него ключ по умолчанию — ваш OPENAI_API_KEY. После патча при отсутствующем именованном ключе llm сразу падает с ошибкой «No key found», ничего никуда не отправляя. The first one (GHSA-v9h7-jj4g-f862) hit models whose config sets both api_base and api_key_name — meaning the author explicitly told llm to use a separate, named key for that endpoint. If that named key was never stored (you just hadn't gotten around to adding it), the tool didn't refuse the request — it silently fell back to the default key, your OPENAI_API_KEY. After the patch, a missing named key now fails fast with a "No key found" error instead, sending nothing.

Вторая (GHSA-r639-rr7r-x72w) — более хитрая комбинация: модель с флагом responses: true (значит, обычно она использует новый OpenAI Responses API) и своим api_base, запущенная с флагом совместимости -o chat_completions 1 (который переключает именно на старый формат chat-completions). Та же история случалась и при прямом вызове llm openai endpoint URL --responses -o chat_completions 1 без явного --key. В обоих случаях комбинация флагов сбивала логику выбора ключа, и в сторонний api_base утекал сохранённый ключ провайдера openai или OPENAI_API_KEY — ровно тот секрет, который должен использоваться только для api.openai.com. The second (GHSA-r639-rr7r-x72w) was a trickier combination: a model with responses: true (meaning it normally talks to OpenAI's newer Responses API) and its own api_base, run with the compatibility flag -o chat_completions 1 (which switches it to the older chat-completions format). The same thing happened calling llm openai endpoint URL --responses -o chat_completions 1 directly without an explicit --key. In both cases the flag combination confused the key-selection logic, and the stored openai provider key or OPENAI_API_KEY leaked to the third-party api_base — the exact secret meant only for api.openai.com.

Зачем это тем, кто просто пользуется LLM-тулингомWhy this matters even if you just use LLM tooling

Урок здесь не «обновите llm» (хотя да, стоит), а более общий: любой CLI или библиотека, которая умеет работать «с любым OpenAI-совместимым сервером» одним и тем же набором ключей, по умолчанию рискует смешать «ключ для настоящего OpenAI» и «ключ/отсутствие ключа для стороннего эндпоинта» — особенно на стыке двух разных режимов совместимости (как здесь — Responses API против chat-completions). Если вы сами настраиваете прокси, self-hosted модели или локальные inference-серверы под OpenAI-совместимым API в любом инструменте, это повод проверить, не течёт ли туда ваш настоящий ключ провайдера «по умолчанию», а не специально выданный под этот эндпоинт — и в идеале заводить для каждого стороннего api_base свой отдельный, скоупированный ключ, а не полагаться на то, что инструмент сам не перепутает. The lesson isn't just "update llm" (though you should) — it's more general: any CLI or library that can talk to "any OpenAI-compatible server" through one shared set of keys risks blurring "the key for the real OpenAI" and "the key, or lack of one, for a third-party endpoint" — especially at the seam between two compatibility modes, as happened here with the Responses API versus chat-completions. If you configure proxies, self-hosted models, or local inference servers behind an OpenAI-compatible API in any tool, it's worth checking whether your real provider key leaks there by default instead of a key scoped specifically for that endpoint — and ideally giving every third-party api_base its own separate, scoped key rather than trusting the tool not to mix them up.

Отдельно в том же релизе — не связанные с безопасностью, но практичные исправления: поддержка вложений (-a/--attachment) через пайпы вроде bash-подстановки процессов, более понятная ошибка на пустом вложении вместо трейсбека, починка парсинга YAML в extra-openai-models.yaml при отступах или завершающем маркере ..., и фикс в Python API: переоткрытие коллекции эмбеддингов с другой моделью теперь использует модель, сохранённую в самой коллекции, а не смешивает векторы от двух разных моделей в одном хранилище. Separately in the same release — not security-related, but practical: attachment support (-a/--attachment) now works through pipes such as bash process substitution, an empty attachment now shows a clear error instead of a traceback, YAML parsing in extra-openai-models.yaml is fixed for indentation and a trailing ... marker, and in the Python API, reopening an embedding collection with a different model now uses the model stored on the collection itself instead of mixing vectors from two different models in one store.
