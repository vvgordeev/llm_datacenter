Как команда Claude Code думает о верификации: три вида тестов, чек-лист на 39 пунктов и три попытки до передачи человеку How the Claude Code team thinks about verification: three kinds of tests, a 39-item checklist and three tries before handing off to a human

Источник ↗Source ↗

Команда Claude Code утверждает, что около 90% кода в их собственном продукте сейчас пишет и проверяет сам Claude — и статья объясняет не это число само по себе, а то, что оно опирается не на доверие к модели, а на систему верификации, которая делает самостоятельную проверку результата дешевле и надёжнее ручного код-ревью. Идея отправной точки простая: по мере того как агент берёт на себя всё больше рутинных проверок — линтеры, тайп-чекеры, падающие тесты, — человеку остаётся формализовать именно те проверки, которые раньше держались в голове и выполнялись «по памяти», превратив их в скиллы, которые Claude применяет автоматически, а не каждый раз полагаясь на то, что о них вспомнят. The Claude Code team says roughly 90% of the code in their own product is now written and reviewed by Claude — and the article is really about what backs that number, not the number itself: not trust in the model, but a verification system that makes checking the model's own output cheaper and more reliable than manual code review. The starting idea is simple: as the agent absorbs more of the routine checks — linters, type checkers, failing tests — what's left for a human is to formalize exactly the checks that used to live in someone's head and run "from memory," turning them into skills Claude applies automatically instead of relying on someone remembering to run them.

Три вида тестов вместо одногоThree kinds of tests instead of one

Статья выделяет три инструмента проверки, которые команда считает обязательным минимумом, а не выбором по вкусу. Сквозные (end-to-end) тесты реальных пользовательских сценариев идут первыми — они ловят то, что любые юнит-тесты пропускают по конструкции. Property-тесты (на инструментах вроде fast-check, Hypothesis или proptest) генерируют тысячи случайных входных данных и проверяют не конкретный пример, а инвариант — то, что должно оставаться верным при любых входных значениях. Дифференциальные тесты применяются отдельно — при миграциях они сравнивают поведение старой и новой системы напрямую, вместо того чтобы заново описывать ожидаемый результат руками. The article names three verification tools the team treats as a mandatory baseline, not a matter of taste. End-to-end tests of real user flows come first — they catch what unit tests miss by construction. Property tests (using tools like fast-check, Hypothesis or proptest) generate thousands of random inputs and check not a specific example but an invariant — something that should hold true for any input. Differential tests are kept separate — for migrations, they compare the old system's behavior against the new one directly, instead of re-describing the expected result by hand.

Чек-лист на 39 пунктов и три попытки до эскалацииA 39-item checklist and three tries before escalation

Помимо тестов команда ведёт чек-лист примерно из 39 пунктов, каждый из которых привязан к условию, считываемому прямо из диффа, — то есть Claude не прогоняет все 39 проверок на каждое изменение, а применяет только те, чьё условие сработало (обычно от 3 до 10 пунктов на один диф). Авторы говорят, что пункты чек-листа появились не абстрактно, а напрямую из истории инцидентов и пул-реквестов — каждый пункт существует потому, что когда-то его отсутствие привело к реальному сбою. Скилл верификации (verify-skill) хранится в `.claude/skills/`, запускает и наблюдает приложение в действии, а если фикс не проходит проверку три раза подряд, Claude прекращает попытки и передаёт задачу человеку, а не зацикливается на подборе решения. Коммит-гейт требует прохождения `/code-review` или `/verify` на каждое изменение, а не только там, где автор сам решил их запустить, и при этом сами проверяющие правила читаются из основной ветки, а не из PR, — так что изменение не может отредактировать тот самый чек-лист, который его же и судит. Beyond tests, the team keeps a checklist of roughly 39 items, each tied to a trigger readable straight from the diff — so Claude doesn't run all 39 checks on every change, only the ones whose trigger fires (typically 3 to 10 per diff). The authors say the checklist items weren't drafted in the abstract; they came directly from the history of outages and pull requests — each item exists because its absence once caused a real failure. The verify skill lives in `.claude/skills/`, runs and observes the app in action, and if a fix fails the check three times in a row, Claude stops trying and hands the task to a human instead of looping on the same fix. A commit gate requires `/code-review` or `/verify` to pass on every change, not only where the author chose to run them, and the rules those checks apply are read from the base branch rather than the pull request itself — so a change can't edit the very checklist that judges it.

Почему это важно не только для Claude CodeWhy this matters beyond Claude Code itself

Главный практический вывод статьи переносится на любую команду, которая передаёт агенту больше автономии: чем шире агент действует самостоятельно, тем важнее не «больше доверия», а система проверки, которая умеет сама остановиться и спросить человека, когда повторный фикс не работает. Привязка чек-листа к реальным инцидентам, а не к абстрактным best practices, и запрет на саморедактирование правил проверки — это конкретные, переносимые приёмы, а не просто внутренняя практика одной команды. The article's central practical takeaway transfers to any team handing an agent more autonomy: the wider an agent's autonomy, the more what matters isn't "more trust" but a verification system that can stop itself and ask a human when a repeated fix isn't working. Tying the checklist to real incidents rather than abstract best practices, and barring the checked change from editing its own checking rules, are concrete, transferable techniques rather than just one team's internal habit.
