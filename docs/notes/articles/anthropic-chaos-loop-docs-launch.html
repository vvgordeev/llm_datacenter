«Chaos loop»: две недели Claude ломал Claude Docs сам, чтобы найти слабые места до запуска The "chaos loop": two weeks of Claude trying to break Claude Docs itself, before launch

Источник ↗Source ↗

Перед запуском Claude Docs инженеры Anthropic две недели держали на стейджинге непрерывный цикл: Claude самостоятельно пытался сломать сервис, а не просто прогонял заранее написанный набор тестов. Итог, который статья выносит в заголовок, — на 2 миллиарда реальных запросов после запуска пришлось всего 60 ошибок сервера, и ни разу не потребовался откат. Это не история про «ИИ нашёл баги» в общем смысле, а конкретный, воспроизводимый процесс: управляющая сессия Claude Code выбирает сценарий нагрузки, прогоняет тестовый стенд, читает телеметрию, предлагает исправление и выкатывает его на стейджинг — и повторяет цикл заново, без паузы на человека на каждой итерации. Before launching Claude Docs, Anthropic's engineers ran a continuous loop on staging for two weeks: Claude tried to break the service on its own, rather than just running a pre-written test suite. The headline result the article leads with is that across 2 billion real requests after launch, there were only 60 server errors, and the team never had to roll back. This isn't a generic "AI found bugs" story but a specific, repeatable process: a long-running Claude Code session picks a load scenario, runs the test harness, reads the telemetry, proposes a fix, and ships it to staging — then repeats the cycle without pausing for a human at every iteration.

Как устроен сам цикл: координатор и до тридцати агентовHow the loop itself is structured: a coordinator and up to thirty agents

По пересказам статьи, цикл управлялся координирующей сессией, которая могла распределять работу между до тридцатью под-агентами одновременно — каждый отрабатывал свой сценарий нагрузки или класс ошибок параллельно с остальными. Важное ограничение, которое команда закладывала намеренно: всё, что сложно откатить — например, изменения схемы данных, — уходило на решение человека, а не автоматизировалось в общем цикле. То есть масштаб автономии был не «агент делает всё подряд», а «агент делает всё обратимое, а необратимое — эскалирует». According to write-ups of the article, the loop was run by a coordinating session that could spread work across up to thirty sub-agents at once — each working its own load scenario or error class in parallel with the others. One constraint the team built in deliberately: anything hard to undo, such as schema changes, went to a human decision rather than being automated inside the loop. So the scope of autonomy wasn't "the agent does everything" but "the agent does everything reversible, and escalates everything that isn't."

Главный урок: система должна быть читаемой для моделиThe main lesson: the system has to be legible to the model

Статья формулирует ключевое условие, при котором такой цикл вообще работает: он замыкается на исправления только тогда, когда система на каждой итерации выдаёт точную телеметрию — если модели не на что опереться при оценке результата своей же правки, цикл не сходится к улучшению. Отдельно упоминается эффект «дрейфа цели» (goal drift): на длинных прогонах, через десять-двадцать итераций, модель начинает забывать, какую именно метрику она изначально оптимизировала, и начинает чинить не то. Это не абстрактная оговорка, а практическое ограничение метода — то, ради чего нужен внешний контроль цикла, а не просто доверие к тому, что «агент сам разберётся», если прогон длинный. The article states the key condition that makes a loop like this work at all: it only closes the loop on fixes when the system produces accurate telemetry on every iteration — if the model has nothing solid to evaluate its own change against, the loop doesn't converge toward improvement. It separately names a "goal drift" effect: on long runs, after ten to twenty iterations, the model starts forgetting exactly which metric it was optimizing for in the first place, and starts fixing the wrong thing. That's not an abstract caveat but a practical limitation of the method — the reason the loop needs outside oversight rather than just trusting that "the agent will sort it out" on a long run.
