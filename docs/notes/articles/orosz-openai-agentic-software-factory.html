Внутри агентной софтверной фабрики OpenAI Inside OpenAI's agentic software factory

Оригинал статьи ↗Original article ↗

Идея «софтверной фабрики»: не генерация кода, а замкнутый цикл с обратной связьюThe "software factory" idea: not code generation, but a closed feedback loop

Гергей Орос описывает, как внутри OpenAI устроены несколько автоматизированных, агентных петель обратной связи, которые компания использует для собственной разработки. Центральное различие, которое подчёркивает статья: это не просто генерация кода по запросу, а агент (Codex), встроенный в цикл, включающий выполнение, результаты тестов, состояние репозитория и итеративное исправление. Агенту дают доступ к исходному коду и документации, к Git и GitHub, к Slack, Notion, Databricks, Datadog, внутренним логам и внутренне поддерживаемым «навыкам» (skills) — то есть к тому же контексту, которым пользовался бы штатный инженер. Gergely Orosz describes how OpenAI has built several automated, agentic feedback loops it uses for its own software development. The key distinction the article draws: this isn't just on-demand code generation — it's an agent (Codex) embedded in a loop involving execution, test results, repository state, and iterative correction. The agent is given access to source code and documentation, Git and GitHub, Slack, Notion, Databricks, Datadog, internal logs, and internally maintained "skills" — essentially the same context a staff engineer would use.

Пример «Perf Factory»: от продакшена — обратно в разработкуThe "Perf Factory" example: from production back into development

Показательный пример из статьи — Perf Factory: система мониторит продакшен и сама запускает агентов Codex для исправления проблем с производительностью. Механика такая: агент вносит изменение, собирает софт, прогоняет тесты и чинит падения, создаёт или обновляет пул-реквест, а CI параллельно выполняет более полный набор линтеров и тестов; агент затем сам отслеживает статус пул-реквеста, интерпретирует обратную связь от CI, дорабатывает изменение и повторяет цикл, пока проверки не станут зелёными. Для оценки влияния на производительность агент прогоняет проблемные пул-реквесты через отдельный perf-харнесс и фреймворк синтетических A/B-тестов (Synthetics A/B) — то есть решение «стало ли лучше» тоже принимается по измеримому сигналу, а не на глаз. A telling example from the article is Perf Factory: a system that monitors production and automatically kicks off Codex agents to fix performance regressions. The mechanics: the agent makes a change, builds the software, runs tests and fixes failures, opens or updates a pull request, while CI runs a fuller set of linters and tests in parallel; the agent then monitors the PR's status itself, interprets CI feedback, revises the change, and repeats the cycle until checks turn green. To judge the performance impact, the agent runs problematic PRs through a dedicated perf harness and the Synthetics A/B testing framework — so the "did this actually get better" call is also made on a measurable signal, not by eyeballing it.

Результат: рост пропускной способности — и 10-кратная нагрузка на инфраструктуруThe result: higher throughput — and 10x load on infrastructure

По описанию статьи, у такого подхода быстрое распространение внутри компании — как среди инженерных, так и среди неинженерных команд, — и заметно более высокая пропускная способность разработки за счёт новых петель обратной связи, замыкающих продакшен на разработку. Но та же автоматизация создала примерно десятикратную нагрузку на часть систем разработки и подняла вопросы о том, как в таких объёмах вообще устроено ревью пул-реквестов человеком. Важная деталь, которую подчёркивает автор: автоматизация не устранила необходимость в человеческом одобрении, операционной экспертизе или дежурных инженерах (on-call) — агентная фабрика ускоряет цикл, но не убирает человека из контура принятия решений. Per the article, this approach spread rapidly across the company, both in engineering and non-engineering teams, delivering substantially higher development throughput thanks to the new feedback loops connecting production back to development. But the same automation created roughly 10x load on some development systems and raised open questions about how pull-request review by humans can even work at that volume. A key detail the author stresses: the automation hasn't eliminated the need for human approval, operational expertise, or on-call engineers — the agentic factory speeds up the loop, but doesn't remove the human from the decision loop.

ОграниченияLimitations

Это описание внутренней инфраструктуры одной компании (OpenAI) на основе интервью с её сотрудниками, а не воспроизводимый рецепт с открытым кодом — конкретные пороги, при которых Perf Factory считает изменение «регрессией», и детали интеграции с внутренними инструментами (Databricks, Datadog и др.) в статье не раскрываются полностью. Само явление десятикратной нагрузки на инфраструктуру и нерешённый вопрос масштабирования человеческого ревью показывают, что подход пока не «закрыт» даже для самой OpenAI, а находится в процессе донастройки. This is a description of one company's (OpenAI's) internal infrastructure based on interviews with its staff, not a reproducible open-source recipe — the article doesn't fully disclose the specific thresholds Perf Factory uses to flag a change as a "regression," or the integration details with internal tools like Databricks and Datadog. The 10x infrastructure load and the still-open question of scaling human review show the approach isn't a solved problem even for OpenAI itself — it's still being tuned.
