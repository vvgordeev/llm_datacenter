Низкая точность на входе — дешевле, чем чинить готовый кодLow fidelity going in is cheaper than fixing finished code

Разница результатов между обычным запросом и «гриллированным» наглядно сравнивается на экране [05:29]: Покок объясняет, что текстовый диалог-«гриллинг» на раннем этапе — самый дешёвый способ выявить и устранить фундаментальную проблему в постановке задачи, потому что стоимость правки растёт по мере продвижения к готовому коду. Дешевле поймать неверную предпосылку в текстовом вопросе, чем в уже написанном и, возможно, слитом в прод коде. Далее видео подробно разбирает внутреннее устройство самих скиллов /grill-me и /grilling — как они закодированы как серия связанных LLM-инструкций, а не как один монолитный промпт [09:19]. A side-by-side of a plain request versus a "grilled" one makes the gap concrete on screen [05:29]: Pocock's point is that a cheap, text-only "grilling" conversation up front is the cheapest place to catch a broken premise in a task, because the cost of fixing it only grows the closer you get to finished code. Catching a bad assumption in a text question is cheaper than catching it in code that's already written — and possibly already shipped. The video then walks through how the /grill-me and /grilling skills themselves are built — as a series of linked LLM instructions rather than one monolithic prompt [09:19].

«Main Flow»: весь цикл разработки как цепочка скилловThe "Main Flow": the whole dev cycle as a chain of skills

С 13-й минуты Покок даёт обзор набора скиллов «Main Flow» [13:12] — идея в том, что весь жизненный цикл фичи (написание спецификации, создание тикета, реализация, код-ревью) можно разбить на отдельные, явно закодированные шаги, а не поручать агенту всё сразу одним расплывчатым промптом. Каждый шаг — это отдельный воспроизводимый и проверяемый скилл со своим входом и выходом, а не свободная генерация «как получится». Для параллельного запуска нескольких таких цепочек или агентов на разных задачах Покок упоминает оркестрирующие инструменты вроде Sandcastle, которые позволяют вести несколько кодинг-агентов одновременно в разных контекстах. From the 13-minute mark, Pocock walks through the "Main Flow" skill set [13:12] — the idea being that a feature's whole lifecycle (writing a spec, filing a ticket, implementation, code review) can be broken into separate, explicitly encoded steps instead of being handed to an agent as one vague, do-everything prompt. Each step is its own reproducible, checkable skill with a defined input and output, rather than free-form "however it comes out" generation. For running several such chains or agents in parallel across different tasks, Pocock points to orchestration tools like Sandcastle, which let you drive multiple coding agents at once across separate contexts.

/writing-for-agents: убрать «no-ops» из документации для агента/writing-for-agents: cutting "no-ops" out of agent-facing docs

Ближе к концу видео (21:37) разбирается скилл /writing-for-agents [21:37]: он редактирует инструкции, адресованные агентам (README, SKILL.md, системные промпты), выявляя и удаляя «no-ops» — формулировки, которые ничего не меняют в поведении агента, но добавляют когнитивную нагрузку и увеличивают шанс, что важная часть инструкции потеряется среди воды. Итог, который Покок формулирует как общий принцип всего репозитория: скиллы — это не разовые промпты, а среда, которая может накапливать состояние между сессиями (отслеживать, что агент уже узнал, что уже сделано), и именно поэтому к текстам для агентов стоит применять ту же строгость редактирования, что и к обычной технической документации для людей. Near the end (21:37), the video covers the /writing-for-agents skill [21:37]: it edits instructions meant for agents (READMEs, SKILL.md files, system prompts), finding and cutting "no-ops" — wording that doesn't change agent behavior at all but adds cognitive load and raises the odds that the one instruction that matters gets lost in the noise. Pocock frames this as the repo's underlying principle: skills aren't one-off prompts but an environment that can carry state across sessions (what the agent has already learned, what's already done) — which is exactly why agent-facing text deserves the same editorial rigor as ordinary technical docs written for humans.
