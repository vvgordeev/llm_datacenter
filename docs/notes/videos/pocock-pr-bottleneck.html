Когда кодинг-агенты генерируют код быстрее, чем люди успевают его просматривать, узким местом всего процесса разработки становится не написание, а ревью пулл-реквестов [00:05]. Покок вводит метафору «Фабрики ПО»: агенты и инструменты вроде Codex — это «акселераторы», входы фабрики, которые наращивают скорость производства кода [01:03]. Но фабрика без тормозов — это авария, а не продуктивность: если наращивать только скорость генерации, не наращивая механизмы проверки, затор просто переезжает с написания кода на его ревью. When coding agents generate code faster than humans can read it, the bottleneck in software development shifts from writing code to reviewing it [00:05]. Pocock frames this with a "Software Factory" metaphor: agents and tools like Codex are "Accelerators" — inputs that ramp up the factory's code output [01:03]. But a factory with no brakes isn't productive, it's a crash waiting to happen: scale up generation speed without scaling up checking, and the bottleneck just moves from writing code to reviewing it.

Три уровня «тормозов»: от дешёвого к дорогомуThree layers of "Brakes": cheap to expensive

Решение — выстроить ревью в три слоя по возрастанию стоимости [02:20]: детерминированные автоматизированные проверки (линтеры, тесты, типизация — дёшево, гонять можно на каждый коммит), автоматизированное ревью (отдельный агент сверяет код со стандартами команды) и человеческое ревью — самый дорогой ресурс, который стоит тратить только на критичные решения. Задача — максимально сдвинуть нагрузку в первые два слоя, оставив человеку то, что действительно требует его суждения. The fix is to stack review into three layers of rising cost [02:20]: deterministic Automated Checks (linters, tests, types — cheap enough to run on every commit), Automated Review (a separate agent checks code against team standards), and Human Review — the most expensive resource, to be spent only on what truly needs human judgment. The goal is to push as much load as possible into the first two layers, leaving people the decisions that actually require their judgment.

Автоматизированные проверки умеют «лгать»Automated checks can "lie"

Покок на экране показывает два вида тестов, которым нельзя доверять слепо [05:33]: «тавтологические» тесты, которые проверяют реализацию саму через себя и физически не могут провалиться, и «структурно-чувствительные» тесты, завязанные на внутреннее устройство кода настолько жёстко, что ломаются от любого рефакторинга независимо от того, сломано ли поведение. Отсюда вывод: автоматизированные и человеческие ревью нужны именно как «детекторы лжи» поверх проверок, которые сами могут давать ложное чувство безопасности. Одно из противоядий — дизайн кодовой базы через «глубокие модули», прячущие сложное поведение за простым интерфейсом [08:40]: чем глубже модуль, тем меньше тестов будут завязаны на его внутреннюю структуру, и тем легче агенту писать по нему осмысленные тесты. On screen, Pocock shows two kinds of tests you can't trust blindly [05:33]: "tautological" tests that check an implementation against itself and physically cannot fail, and "structure-sensitive" tests wired so tightly to a function's internals that they break on any refactor regardless of whether behavior actually changed. The takeaway: automated and human review exist precisely as "lie detectors" over checks that can themselves give a false sense of safety. One antidote is codebase design through "deep modules" that hide complex behavior behind a simple interface [08:40]: the deeper the module, the fewer tests end up coupled to its internals, and the easier it is for an agent to write tests that actually mean something.

Разделение «имплементатора» и «ревьюера»Splitting the "implementer" from the "reviewer"

Ключевая практическая рекомендация — не поручать проверку на соответствие стандартам кодирования тому же агенту, который пишет код [11:44]. Стандарты стоит вынести во внешний файл (например, CODING_STANDARDS.md) и поручить их соблюдение отдельному агенту-«ревьюеру»: агент-«имплементатор» и так несёт большую когнитивную нагрузку по самой задаче, и перегружать его ещё и списком стилевых правил — верный способ получить код, который не соблюдает ни то, ни другое как следует. При этом автоматизированное ревью полезнее, когда оно само сразу коммитит мелкие исправления, а не просто оставляет комментарии, которые человеку придётся читать и применять руками. The key practical recommendation is to never let the same agent that writes the code also check it against coding standards [11:44]. Standards belong in an external file (e.g. CODING_STANDARDS.md) enforced by a dedicated reviewer agent: the implementer agent already carries heavy cognitive load from the task itself, and loading it up with a style checklist too is a reliable way to get code that does neither job well. Automated review also pays off more when it commits small fixes directly instead of just leaving comments a human then has to read and apply by hand.

Что по-прежнему должен решать человекWhat's still a human call

Человеческое ревью Покок советует концентрировать на двух сигналах [18:26]: изменения-«двери в одну сторону» (решения, которые дорого или невозможно отменить) и PR с высоким «радиусом поражения» (затрагивающие много систем или пользователей сразу). Для таких PR он показывает скилл /show-me, который готовит человеко-читаемое визуальное объяснение изменения вместо сырого диффа. Ролик закрывается скиллом /retro [20:35]: после каждого инцидента или промаха ревью команда прогоняет ретро не по людям, а по системе проверок — и дополняет автоматизированные проверки или стандарты так, чтобы тот же класс ошибок в следующий раз поймал самый дешёвый из трёх уровней, а не самый дорогой. Pocock says human review should concentrate on two signals [18:26]: "one-way door" changes (decisions that are expensive or impossible to reverse) and high "blast-radius" PRs (touching many systems or users at once). For those, he demos the /show-me skill, which produces a human-readable visual explanation of a change instead of a raw diff. The video closes with the /retro skill [20:35]: after any incident or review miss, the team runs a retro not on the people involved but on the checking system itself — updating automated checks or standards so the same class of bug gets caught by the cheapest of the three layers next time, not the most expensive one.
